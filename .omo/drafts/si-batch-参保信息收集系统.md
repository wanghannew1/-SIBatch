# Draft: 派遣员工参保信息收集系统

## 需求概述（用户原话）
前台业务员导入一张参保信息表或减员表，后台分别生成社保失业工伤的报盘和医保的报盘。社保失业工伤和医保由不同业务人员管理。做简单的分权分账号功能。目标：最快用上。

## 模板结构分析（已读取全部6个文件）

### 输入模板（前台导入）
1. **合同批量导入模板 (增员).xls** — Sheet1 60列
   - R0 注意事项, R1 分组头, R2 列名, R3 格式说明, R4+ 数据
   - 关键列：姓名、身份证号码、民族、人员身份、户口性质、联系电话、合同开始/终止时间、合同工资、
     是否参加养老/失业/医疗/工伤/生育保险、社保参保属地、社保参保年月、医保参保属地、医保参保年月、
     养老/失业/医保/工伤/生育缴费基数、工资账号、发放银行、社保参保状态、医保参保状态、证件类型
   - 辅助Sheet：发放银行（代码-名称）、二级代码（各种下拉字典）
   - 字段值带代码前缀，如 "01-汉族"、"11-本地非农业户口（本地城镇）"、"220100000000-吉林省长春市"

2. **合同解除批量导入模板 (减员).xls** — Sheet1 16列
   - 关键列：姓名、身份证号码、合同终止日期、资料提交年月、社保报减年月、公积金报减年月、医保报减年月、
     工伤报减年月、合同终止原因、是否享受失业金、工资结束年月、是否经济赔偿、社保参保状态、医保参保状态
   - 合同终止原因带代码：如 "01-在试用期被证明不符合录用条件"
   - Sheet2：合同终止原因/是/否/参保状态 下拉字典

### 输出模板（后台生成）
3. **社保失业工伤-增员：企业职工批量参保登记模板.xlsx** — 人员名单 27列
   - R0 说明, R1 单位编号/单位名称, R2 列名, R3 示例行, R4+ 数据
   - 关键列：证件类型、证件号码、姓名、民族、性别、出生日期(yyyyMMdd)、参加工作日期(yyyyMMdd)、
     国籍、农民工标识、人员身份、临时账户标识、申报工资、参保日期(yyyyMMdd)、企业养老(是/否)、
     失业保险(是/否)、工伤保险(是/否)、是否兼职工伤、户口所在地址、常住地址、工作所在地址、联系电话、参保身份、模板版本(1.0)
   - 性别/出生日期可从身份证号推导

4. **社保失业工伤-减员：单位职工停保模板.xlsx** — Sheet1 5列
   - 证件号码、姓名、停保日期(yyyyMMdd)、停保原因、备注
   - 停保原因固定字典(Sheet2)：个人原因解除、用人单位辞退、工作关系调转、人员达到享受养老待遇条件、
     死亡、到龄停保、人员被判刑收监执行、无附件停保、其他原因中断缴费

5. **医保-增员：001 批量职工新参保(增员).xls** — Sheet1 17列
   - 证件类型、证件号码、姓名、性别、民族、出生日期、首次参加工作日期、户口性质、婚姻状态、健康状况、
     居住地址、居住地邮政编码、固定电话、手机号码、申报工资、编制类型、本次参保时间
   - ⚠️ 日期字段是 Excel 日期序列号（如 39070.0），不是文本！
   - 默认值：婚姻状态=未说明的婚姻状况、健康状况=健康或良好、编制类型=非在编

6. **医保-减员：批量减员申报(减员).xls** — Sheet1 3列
   - 姓名、证件类型、证件号码（极简）
   - Sheet2：变更原因字典（在职人员解除/终止劳动合同 等）

## 关键技术发现
- 环境：Python 3.12.3 + openpyxl 3.1.5 + xlrd 2.0.1 + pandas 3.0.2 已就绪
- 工作目录为全新（仅 输入输出 文件夹），git 未初始化 → 全新项目
- 医保输出日期 = Excel 序列号；社保输出日期 = 文本 yyyyMMdd
- 性别、出生日期可从身份证号推导（17位奇偶、7-14位）
- 字段值普遍带"代码-"前缀，需在映射时剥离或映射为输出字典值
- 减员停保原因/医保变更原因需从合同终止原因映射（映射规则待确认）

## 已确认决策
1. 部署方式：**局域网多机访问**（后台一台机器当服务器，前台/其他人浏览器访问该机 IP）
2. 公积金：**暂不纳入**（输入有公积金字段但无输出模板；架构预留扩展，后续升级再加）
3. 减员原因映射：**后台可配置**（映射表存 DB + 管理页面编辑，预置默认映射，生成时自动套用）
4. 单位信息（单位编号/名称）：**管理员在系统里可配置**（社保/医保各一套，生成时自动带入）
5. 意外险字段：默认忽略（输入有意外险维护列，但无对应报盘模板；数据仅留存不生成报盘）
5b. **生育保险、历史补录：不纳入本期范围**（社保增员报盘仅含养老/失业/工伤，无生育列；历史补录无输入路径，不实现补缴逻辑）

## 新增确认（第二轮）
6. 申报工资：社保和医保的「申报工资」都取「合同工资」（基数一般与合同工资一致）
7. 医保减员：保持3列（姓名/证件类型/证件号码），不追加合同终止原因
8. 日期规则：
   - 社保 参保日期 = 合同开始时间
   - 社保 停保日期 = 合同终止日期
   - 省医保 本次参保时间 = 合同开始时间
   - 市医保 本次参保时间 = 医保参保年月 + 01（如202006→20200601）
9. ⚠️ 新发现：医保分「省医保」和「市医保」（依据输入表「医保参保属地」区分，如 2299...省直=省医保、2201...长春市=市医保）
   - 待确认：是否要生成成两个独立报盘文件？医保管理员是一个还是省/市两个？

## 新增确认（第三轮）
10. 省/市医保区分：按「医保参保属地」判断（2299...省直=省，2201...长春市=市）
11. 医保报盘：分成省医保、市医保两个独立文件（增员、减员各分开，方便报送不同医保局）
12. 医保管理员：一个人管，生成时分别出省/市文件
13. **省工伤独立模块**：
    - 省工伤减员需单独生成「单位职工停保模板」格式报盘（与社保减员同格式）
    - 省工伤人员名单目前在"原始库"中，用户后续手动导入本系统
    - 需单独建立「省工伤人员信息表」，支持导入/查看/编辑/删除
    - 待确认：省工伤是否只需减员？增员是否需要？字段结构？归谁管？

## 最终确认（第四轮）
14. 省工伤：**只做减员报盘**（增员走市社保增员，含工伤）
15. 省工伤人员信息表字段：证件号码、姓名、结算单元、合同开始时间等，**按增员模板(60列)字段设计，保留冗余字段但不一定用**
16. 省工伤归**社保管理员**管理

## 最终确认决策
1. 技术栈：**Flask 单体**（Python + Flask + SQLite + Jinja2 + Bootstrap，服务端渲染，无前端构建）
2. 测试策略：**仅 Agent 执行验证**（无自动化单元测试；每任务由执行代理跑通真实模板验证字段/格式）
3. 硬性约束：**不硬编码** — 所有可变业务数据（减员原因映射、单位信息、字典映射、默认值）走 DB + 后台配置页面
4. 减员原因映射：DB 表 + 管理页面可编辑，预置默认映射，生成时自动套用
   - **社保减员报盘末尾追加「合同终止原因」列**（原有5列 + 追加原始合同终止原因，与映射后停保原因并列，方便核对）
   - 停保原因仍按固定9值字典映射（后台可配置）
5. 单位信息：DB 表 + 设置页（社保/医保各一套）
6. 意外险字段：忽略（无对应报盘模板，数据留存不生成报盘）

## 数据库决策
- **SQLite（单文件，零运维）**：量级小（个位数账号、每天几次导入、累计万~几十万条），单机 Flask 进程串行访问无并发瓶颈，完全够用，不换 MySQL/PostgreSQL
- 用薄数据访问层封装，未来量级暴涨时便于迁移

## 默认方案（可被推翻）
- 技术栈：Python + Flask + SQLite + Jinja2 + Bootstrap（单体应用，服务端渲染，无需前端构建）
- 角色：前台业务员（上传）、社保管理员（生成+下载社保报盘）、医保管理员（生成+下载医保报盘）、admin（管账号+管映射+管单位信息）
- 工作流：前台上传 → 记录入库 → 两个管理员各自独立生成并下载对应报盘 → 标记完成
